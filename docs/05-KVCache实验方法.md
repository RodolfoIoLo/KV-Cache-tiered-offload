# KV Cache 实验方法

本文给出 KV Cache 分层缓存系统的评测方法与正确性检查，适用于设计和复现实验；不包含服务器性能结果。实验应先通过小范围筛选，再对关键条件重复测量。

## 1. 把研究问题写成能被推翻的句子

| 问题 | 可测假设 | 必须观察 |
|---|---|---|
| RQ1 容量 | KV 逻辑数据量随累计 token 数近似线性增长 | 模型结构、逻辑 bytes、物理块、框架池 |
| RQ2 复用 | 对足够长的兼容前缀，恢复比重算更省时 | 命中长度、恢复/注入时间、被省去的计算 |
| RQ3 SSD | 三层在容量压力下提高有效命中或成功服务能力 | 实际磁盘读、TTFT/ITL/goodput、CPU 与写入代价 |
| RQ4 机制 | 受限预算的预取/批量 I/O 能减少暴露等待 | 对照、stall、带宽、无效读取、tail latency |
| RQ5 活跃卸载，可选/按任务要求 | 超出 GPU KV 常驻容量仍可正确生成 | 真正活跃工作集、每步取回 bytes、TPOT 与 OOM |
| RQ6 多机，可选 | 真实网络条件下，远端恢复或 PD 的收益超过转移成本 | 同总资源对照、网络时间、TTFT/ITL、goodput |

先写出失败条件。例如“预取提高带宽但 p99 ITL 明显变差，或额外读字节失控”就不支持它改善服务质量的假设。

## 2. Baseline 必须把缓存效应拆开

| 编号 | 条件 | 用途 |
|---|---|---|
| B0 | GPU 常驻、无外部缓存、关闭跨请求 APC | 输出 oracle；重复 prefill 的重算成本 |
| B1 | GPU 常驻、无外部缓存、开启 GPU APC | 已有优化的强基线 |
| B2 | GPU + DRAM，GPU APC 设置与对照一致 | 外部 DRAM 缓存的边际价值 |
| B3 | GPU + DRAM + SSD，策略保持简单固定 | SSD 的容量收益与代价 |
| B4 | B3 + 唯一待测机制 | 隔离待测改动的贡献 |

比较 B2/B3 时要记录 GPU APC 的相同配置与实际 hit；“相同开关”仍可能因保留块数不同而导致命中不同，这也是必须测量的中间变量。

可以做两组实验：一组控制每一级命中，隔离组件；另一组让真实策略自然运行，观察整体服务。不要混成一张图。

**公平边界**：正确性在 all-GPU 能运行的相同工作负载上比较。容量扩展时 baseline 可能 OOM，此时报告成功/失败与最大可承载量，不能给 OOM 虚构延迟，也不能计算不存在的“相对加速”。

若 B2/B3 只保存已经结束的请求，它们可能提高可保留会话数，但**没有证明单个活跃请求能超显存运行**。

## 3. 正确性分三层验证

### 3.1 字节、布局和对象身份

在计算之前验证：

- K/V shape、dtype、stride/布局和 byte count 与 consumer 契约一致。
- 保存/恢复的内容在无损路径上 checksum 或逐元素一致。
- layer、token block、head/shard、position 与模型语义没有错位。
- 未完成写入不会被标成可命中，正在读/写的 buffer 不被释放或复用。
- 缓存 key 覆盖必要身份，错误 revision、adapter、prefix、位置不会错误复用。

Checksum 不证明“这份 KV 属于这个请求”，所以还要验证身份和模型层级。

### 3.2 固定 token 的 teacher-forcing logits 比较

使用固定 prompt 和固定后续 token 序列，在每一步比较 all-GPU 与恢复/卸载路径的 logits。这样一旦出现偏差，可以定位首次偏差，不会被贪心选错后不断扩大的上下文差异淹没。

记录最大绝对误差、相对误差、argmax 是否相同、首次不一致位置。相对误差对接近零值不稳定，应同时报绝对误差。

### 3.3 真实生成逐 token 比较

在相同模型/revision、tokenizer、模板、位置设置、精度、backend、采样和输入下，对完整输出 token IDs 比较。先单请求、固定长度/停止规则、greedy、关闭 dropout，并按环境要求设置确定性选项。

**无损缓存路径应以逐 token 一致为验证目标。** 温度为 0 不足以保证跨不同 batch、kernel 或执行顺序 bitwise 一致。若不同路径改变计算顺序产生数值差异：

1. 先排查未同步、错误布局、位置、mask 和 cache key 等真正错误。
2. 在相同执行路径下检查 KV 往返是否无损；再用 teacher forcing 定位数值差异。
3. 把 token 不一致原样报告；误差容限应事先说明并与任务要求对齐。
4. 不得用“浮点误差”掩盖错误，也不能用语义近似替代事先声明的逐 token 一致标准。

**建议用例**：

| 用例 | 要抓的错误 |
|---|---|
| 短/长 prompt，边界长度 `q-1/q/q+1` | 块边界、padding、尾块有效长度 |
| 完全命中、部分前缀命中、完全未命中 | 前缀长度、后缀处理 |
| 仅最后一个 token 不同 | 错误共享尾块 |
| 相同片段但前置上下文不同 | 错误地按片段文本复用 |
| 交错多请求、共享前缀、提前结束/取消 | 引用计数、跨请求污染、回收 |
| GPU/DRAM 容量受限、强制降层再读 | 真正测试卸载路径 |
| 模型/adapter/position 配置变更 | 缓存失效语义 |
| 缺失对象、失败保存、过期索引 | 安全 miss/重算与错误回退 |

## 4. 工作负载怎样构造

第一轮先控制一个变量，确认机制；第二轮才引入真实分布。

| 维度 | 初始建议值 | 注意事项 |
|---|---|---|
| 输入长度 | 512、2048、8192；支持时再试 32768 | 必须在模型支持窗口内，且保留输出空间 |
| 输出长度 | 先约 64 个 token，再加入长输出 | 固定停止规则；实际完成数必须记录 |
| 并发 | 1、4、8，依据显存再调整 | 并发请求数不等于每一步实际 batch |
| 前缀重用 | 0%、约 50%、约 90% token reuse | 用实际命中计数验证，不只看生成器目标 |
| 会话集合 | 可放进 HBM、超 HBM 但进 DRAM、超 DRAM | 明确研究会话容量还是活跃工作集 |
| 到达方式 | 先固定并发，再选开环到达率 | 单独报告，避免协调遗漏与隐含降载 |

这些是起始范围，不是预设硬件能运行的承诺。

用固定种子、公开许可文本或自己生成的可分享文本构造输入，保存 token ID、tokenizer revision 与工作负载哈希。用真正共享的前缀而非“文本看起来像同一主题”。不要用私有会话数据作公开样例。

至少覆盖四类负载：

- **无复用**：证明保存/索引不会在 miss 场景中造成不可接受开销。
- **公共长前缀**：测试共享带来的重算节省与缓存热点。
- **多轮会话、有间歇**：测试会话保留与恢复。
- **容量压力/热点变化**：测试淘汰、提升和预取污染。

活跃卸载另加：固定活跃序列和不断增长的上下文，测每 step 访问的低层字节，确认没有因隐式截断、滑窗或稀疏化改变计算任务。

## 5. 怎样证明发生了真正的卸载和 SSD 回读

### GPU 层

外部缓存命中实验中，复用请求前应按所选框架支持的方法确保对应 GPU KV 不再可命中，并记录实际 GPU hit 与外部读取。仅重新发送同一个 prompt，极可能测到 GPU APC。

### DRAM 层

强制目标对象不在应用 DRAM tier 中，保留 SSD 副本；记录 eviction/placement 和恢复字节。不要同时把它从所有层删掉，然后把重算误当成 SSD miss 路径。

### 内核 page cache 与 SSD

分别报告：

1. **warm buffered**：数据可能在页缓存，代表此条件下应用路径。
2. **cold-data buffered**：采用获准且有证据的冷数据方法，记录不确定性。
3. **direct I/O**：确认 API/后端真的启用，满足对齐并处理不支持情形。

通过设备 I/O 计数、后端实际读 bytes、跟踪或其它可用指标佐证物理读取。共享设备上的系统总计数需要隔离背景流量或说明污染，不能直接全算给自己的进程。

当前协议不要求在共享服务器执行全局 drop_caches，也不要求接管裸盘。缓存预热、对象清理和测量窗口都记录在 run manifest。

## 6. 微基准先回答路径问题

| 微基准 | 扫描维度 | 输出 |
|---|---|---|
| H2D/D2H | 方向、大小、pinned/可用 pageable 条件、并发 | 完成耗时、有效 GB/s、CPU 成本 |
| SSD 读写 | 文件路径、块大小、随机/顺序、队列深度、buffered/direct | IOPS、GB/s、p50/p95/p99、CPU、实际 bytes |
| 缓存后端 | put/get/lookup，命中/未命中、对象数量 | 固定开销、元数据时间、payload 时间 |
| 可选网络 | 消息大小、并发、同机/跨机、TCP/RDMA | 完成时延、payload bandwidth、CPU |

只在自己创建的普通测试文件/授权目录中进行存储读写；数据集与目录不符时应先调整配置。文件 microbenchmark 不自动等于 KV 端到端性能。

组件测量需区分提交、完成与持久化：后台 put 返回可能仅表示已接收；能 get 也未必意味着断电后仍存在。本课题若只要求可重算缓存，可明确不研究 crash durability，但不能将它称为已验证的持久存储。

## 7. 端到端指标与计数

每次运行至少采集：

| 类别 | 指标 |
|---|---|
| 正确性 | 比较请求数、token 不一致数、首次差异、logits error、KV 往返检查 |
| 服务 | TTFT、E2E、TPOT、ITL 分布、成功/失败/超时、input/output tokens/s、requests/s |
| SLO | 预先定义阈值、满足条件的请求数、goodput |
| GPU | KV 活跃块、可用块、分配与 reserved、峰值占用、kernel/copy/wait 时间 |
| Host | RSS、应用缓存、pinned 池、CPU 核秒或利用率 |
| I/O | SSD read/write bytes、应用请求 bytes、H2D/D2H bytes、网络 bytes |
| 缓存 | GPU/DRAM/SSD 实际命中，token/byte 命中率，淘汰/提升、预取使用与浪费 |

定义 `read amplification = 实际从低层读取字节 / 真正消费的低层有效字节`，分母为 0 时不定义；单独说明是否包含 padding、重试和预取未使用数据。

预取有效率可用“在定义的生命周期/窗口内被消费的预取有效字节 / 所有预取有效字节”，同时记录是否按时到达。只报有效率不报 GPU stall，会漏掉“都用上了但都晚了”的情况。

使用阶段分解图时注意重叠：各阶段 wall time 的简单求和可能超过 E2E。分别画时间线和关键路径暴露等待，不把并行的 read 与 compute 都加进一个假想串行总量。

## 8. 统计与运行顺序

1. 固定模型、tokenization、版本与配置；每个 run 唯一 ID。
2. 将 JIT、模型加载、预热与 steady state 分开，声明是否包括启动成本。
3. 先小规模 smoke check，再做至少若干次独立重复；初步可从 5 次开始，根据差异和噪声增加，而非机械固定。
4. 对条件交错或随机顺序运行，记录共享机器干扰、温度/频率与异常。
5. 保存每次记录，报告重复间方差或区间；尾延迟需要足够请求样本。小样本 p99 标明不稳定。
6. 端到端保留所有失败，报告总提交数、完成数与超时；说明截止时仍在队列中的请求怎样处理。
7. 使用开环负载时记录计划发送与实际发送时间，防止客户端瓶颈使目标到达率没有真正达到。

若预计差异只有几个百分点而环境波动更大，优先改善测量条件，不能从噪声里挑最好的一次。

## 9. 最终至少需要的图与表

- KV 逻辑容量/物理块随 token 与并发增长，附公式与差值解释。
- 恢复 vs 重算耗时随前缀长度变化，标出实际盈亏区间。
- 各 baseline 的 TTFT 与 ITL/TPOT，按命中/容量压力分组。
- 固定 SLO 下 goodput 或可承载到达率/并发；附失败率。
- 字节与阶段分解：为什么快、慢在哪里，有无额外写回与读放大。
- 唯一机制的消融图，包含不利场景；多机只有在实际做过时另加。

图上写单位、样本量、模型、硬件、配置编号和误差含义；不用同一张轴把不同资源预算下的值画成公平加速对比。

## 10. 一次实验的保存契约

一次可复现实验至少保存以下内容：

```text
results/<run-id>/
  manifest.json          环境、版本、命令、工作负载、缓存状态
  config.*               实际配置，小文件
  requests.jsonl         每请求结果；公开前脱敏
  counters.json          字节/命中/阶段计数
  summary.csv            聚合值
  analysis.md            结论、异常和下一步
```

大规模原始 traces、模型权重、KV 张量留在忽略目录或合适的数据存储，只提交可分享的小样本、哈希、获取方法。公开产物应说明配置、获取方式和验证状态。

## 11. 看到现象后怎样继续

| 现象 | 候选原因 | 下一步证据 |
|---|---|---|
| 第二次 TTFT 下降 | GPU APC、DRAM、page cache 或真实 SSD reuse | 分层 hit 与 read bytes，受控清理目标层 |
| SSD 带宽低、CPU 忙 | 小 I/O 固定开销、序列化、锁、拷贝 | 分解 CPU、增大批量/块、观察设备队列 |
| 带宽已接近有效上限、GPU 等待 | 搬运量本身过大 | bytes/token 下界；减少多读或调整研究目标 |
| 预取提高平均值但 p99 变差 | 带宽争抢、排队、内存污染 | in-flight/队列、按时命中、写回干扰 |
| 显存池不变但可跑更大并发 | 池预分配、块回收有效 | 可用块、峰值活跃数、成功率 |
| 多机比单机慢 | 转移成本、资源布局或负载不合适 | 网络模型、相同预算、真实路径与排队 |

分析顺序是：先确认正确性与真实路径，再看资源瓶颈，最后才增加复杂机制。
