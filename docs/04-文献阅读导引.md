# 文献阅读导引

KV Cache 研究涉及模型计算、内存管理、存储和调度。以下按问题依赖组织文献：先理解缓存成立的条件，再理解容量管理，最后观察分层存储与跨设备传输。数学基础见 [入门导读](01-LLM生成与KVCache入门.md) 和 [前置知识](02-KVCache计算与存储原理.md)。

## 2. Transformer：缓存成立的计算基础

原论文讨论 encoder-decoder 架构。理解 decoder-only 语言模型的 KV Cache，需要重点关注 masked self-attention，而不是完整复现翻译模型的训练过程。

关键问题包括：

- `QKᵀ` 的 shape 是什么，各维代表什么？
- softmax 作用在哪个维度，为什么要屏蔽未来位置？
- 固定模型与前缀时，追加一个 token 会改变哪些计算？
- 为什么每层各有一份 KV，历史 Q 为什么通常无需保留？

一个有用的检验是画出两层、四个位置的依赖关系，再追加第五个位置，区分可复用状态与必须新算的状态。固定前缀后，完整重算与增量计算应具有相同的模型语义。

## 3. PagedAttention：从逻辑序列到物理块

先理解内存浪费的来源：为可能增长的序列预留连续空间，会产生碎片和空闲预留；共享前缀还可能被重复存储。

阅读块映射与共享示意图时，应追踪：逻辑 token 范围 → 逻辑块 → 物理块 → 引用与释放。两个请求共享前缀、后缀不同的例子，可以用于检查尾块写入和 copy-on-write。

需要区分的边界：

- 分页管理优化分配与共享，不自动等于 DRAM/SSD 卸载。
- 缓存逻辑数据量、物理块占用和运行时预分配池不是同一指标。
- 原论文机制与不同版本引擎的 connector、后端和调度实现应分别核对。

## 4. Mooncake：围绕 KV 组织服务

沿论文架构图与请求流程图，追踪以下路径：

```text
前缀查询与复用 → 增量 prefill → KV 传输 → decode
```

分别标记控制消息、tensor payload、执行节点与数据位置。由此观察几个关键权衡：

- 更多 KV 命中与更空闲计算节点之间可能存在冲突。
- 恢复缓存需要的数据搬运，必须与省掉的重算比较。
- Prefill 与 decode 分离能够独立管理资源，也引入交接 KV 的成本。
- 满足 TTFT 和 token 间延迟约束的有效服务能力，比孤立的峰值吞吐更能反映系统收益。

论文中的完整服务架构与开源组件的实现范围不能直接等同。当前接口应依据对应版本的 [官方架构](https://kvcache-ai.github.io/Mooncake/design/architecture.html) 和 [集成文档](https://kvcache-ai.github.io/Mooncake/deployment/integrations/vllm/index.html) 核对。

## 5. 综述：建立机制分类

综述的分类提供三个互相连接的视角：

| 视角 | 关注什么 | 例子 |
|---|---|---|
| 执行与调度 | 何时计算或访问数据 | 预取、流水线、PD 分离 |
| 放置与迁移 | 数据在哪里，怎样移动 | HBM/DRAM/SSD、远端缓存 |
| 表示与保留 | 数据怎样编码、共享或淘汰 | 量化、前缀共享、缓存保留策略 |

一个系统可能跨越多个类别。分类的用途是说明机制和相互影响，不必将每篇论文强行放入唯一格子。

## 7. 从论文结论到可核对的笔记

一份可独立阅读的解析应包含问题、原路径、核心机制、实验条件和局限。作者结论、独立推导和待验证假设需要明确区分；性能数字应附原文图表和相应的硬件、模型、负载及 SLO。

阅读笔记存放在 `notes/`，涉及的前置知识与独立理解可在相应笔记中整理。代码追踪记录“入口函数 → 状态 → 数据流 → 完成条件”，并附具体 commit 和路径。文献与代码之间的差异也是需要记录的证据。
