# 认识项目:KV Cache 分层卸载与协同管理

## 1. 项目要解决什么问题?

一句话总结:

> 当**GPU 显存**放不下越来越多的 KV Cache 时,**把一部分 KV Cache 放到 CPU 内存和 SSD 中,并在需要时及时取回,同时尽量不让模型生成速度明显变慢**.

不妨再看一眼项目名称:

> KV Cache 分层卸载与协同管理

这其中蕴含了四个关键词:
- KV Cache:语言模型生成过程中产生并重复使用的中间数据;
- 分层:数据放在不同速度,容量和价格的存储层;
- 卸载:把暂时不用的数据从 GPU 显存搬到其他地方;
- 协同管理:模型推理框架,GPU,CPU 内存,SSD,网络或缓存系统共同配合.

现在先不探讨细节,可以把项目看做这样一条数据流:

``` plaintext
用户请求
   ↓
LLM 推理框架,例如 vLLM
   ↓
GPU 计算 Transformer
   ↓
需要历史 KV Cache
   ↓
GPU 显存中是否有?
   ├── 有:直接计算
   └── 没有:
        ├── CPU DRAM 中有:从 DRAM 取回
        └── SSD 中有:从 SSD 取回,再送到 GPU
```

## 2. 先理解 LLM 推理在做什么

**LLM 不是一次性生成整段答案**

以用户问:

``` plaintext
"什么是 KV Cache?"
```

为例,模型不是一次性把整个答案算出来,而是大致这样工作:

``` plaintext
输入:"什么是 KV Cache?"
       ↓
预测第一个 token
       ↓
把这个 token 接到输入后面
       ↓
预测下一个 token
       ↓
继续循环
```

这叫自回归生成.

每一步,模型都根据目前已经看到的全部 token,预测下一个 token.

这通常分为两个阶段:

**Prefill**

一次处理用户已有的输入,例如:

``` plaintext
"请解释一下 KV Cache 的原理"
```
*这一阶段主要是处理已有上下文*

**Decode**

逐个生成新token:

``` plaintext
输入:"请解释一下 KV Cache 的原理"
       ↓
预测第一个 token
       ↓
把这个 token 接到输入后面
       ↓
预测下一个 token
       ↓
继续循环

KV → Cache → 是 → 一 → 种 → ...
```

*Decode 阶段每次通常只新处理一个 token,但它需要参考前面所有 token 的历史信息*

## 3. Transformer 中为什么会出现 Q, K, V?

Attention!

可以把 Attention 理解成:

> 当前 token 想从历史 token 中查找哪些信息,并按照重要程度把这些信息汇总起来.

注意只是在汇总当前token的上下文信息,还没有生成新的 token.

每个 token 会被转换成三种向量:

|名称|可以怎样理解|
|---|---|
Query,Q|当前 token 想查询什么
Key,K|每个历史 token 提供什么索引特征
Value,V|每个历史 token 真正提供的信息

计算过程可以**粗略表示**为:

``` plaintext
Q 和所有 K 比较
       ↓
得到每个历史 token 的相关性分数
       ↓
用分数加权所有 V
       ↓
得到当前 token 的上下文信息
```

公式是:
$$
\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

总之吧:
- 当前 token 会产生一个新的 Q;
- 历史 token 的 K 和 V 可以继续使用;
- 历史 Q 通常不需要保存;
- 每一层 Transformer 都有自己的一组 K 和 V.
  
因此,KV Cache 不是文本缓存,也不是模型参数,而是:

**某个具体请求在某个具体生成过程中,每一层 Attention 产生的历史 K/V 张量.**

## 4. KV Cache 为什么可以缓存?

假设输入是:

``` plaintext
A B C
```

模型准备生成下一个 token.

处理完后,模型已经计算出了 A,B,C 在每一层的 K 和 V.

下一步生成 D 时:

``` plaintext
A B C D
```

如果没有 KV Cache,模型可能重新计算 A,B,C,D 的全部 K/V.

有 KV Cache 时:

``` plaintext
A B C 的 K/V: 直接复用
D 的 K/V: 需要进行新计算
D 的 Q: 需要进行新的计算
```

所以 KV Cache 节省的是历史token的重复计算!

这个时候矛盾就出现了!

``` plaintext
KV Cache 越大
   ↓
重复计算越少
   ↓
但需要保存,读取和搬运的数据越多
```

## 5. KV Cache 如何占满显存?

KV Cache的大小大致可以这样估算:

``` plaintext
每个 token 的 KV 大小
= 2 × Transformer 层数
  × KV head 数
  × head dimension
  × 每个元素的字节数
```

> 详细张量形状推导见 [再读 Transformer](./01-再读Transformer.md)。

总大小还要乘以所有请求中的 token 数量之和.

因此以下因素都会增大 KV Cache:

- 上下文更长;
- 同时处理的请求更多;
- batch 更大;
- Transformer 层数更多;
- KV head 更多;
- 使用 FP16,BF16 等数据类型时,每个元素占用更多字节.

例如:

``` plaintext
32 层
32 个 KV heads
每个 head 维度 128
FP16,每个元素 2 字节
```

每个token的 KV 大小约为:

``` plaintext
2 × 32 × 32 × 128 × 2 bytes
= 524,288 bytes
= 512 KiB
``` 

如果上下文达到32K token:

``` plaintext
32,768 token × 512 KiB/token = 16 GiB
```

这还没有计算
- 模型权重;
- 中间激活;
- CUDA runtime;
- 临时缓冲;
- 其他请求的 KV Cache.

所以在长上下文和高并发场景下,KV Cache 很容易成为显存瓶颈.

## 6. 这个项目中的三层存储是什么?

项目重点关注三层:

``` plaintext
GPU HBM / 显存
        ↓
CPU DRAM / 主机内存
        ↓
NVMe SSD
```

它们的特点大致如下:
|层级|容量|速度|访问延迟|作用|
|---|---|---|---|---|
GPU显存HBM|小|最快|最低|当前正在计算的KV
CPU DRAM|较大|较快|中等|GPU显存的溢出区
NVMe SSD|最大|较慢|较高|大规模持久化或冷KV层

这里不能简单理解为"SSD 只是更大的内存".

数据从 SSD 到 GPU,通常要经过多段路径:

``` plaintext
SSD
 ↓
操作系统 / I/O 接口
 ↓
CPU 内存
 ↓
PCle
 ↓
GPU 显存
 ↓
GPU Kernel
```

每一段都会产生:
- 延迟;
- CPU 开销;
- 内存复制;
- 总线占用;
- 同步等待.

因此,把KV放到SSD后,虽然解决了容量问题,但可能导致生成速度严重下降

## 7. 项目真正要实现的功能

### 第一层: 全显存baseline

首先不做任何卸载:所有 KV Cache 都留在 GPU 显存

记录:
- 输出是否正确;
- GPU 显存用了多少;
- TTFT;
- 每秒生成多少 token;
- 不同上下文长度下的表现;
- 不同 batch 大小下的表现.

### 第二层: 加入主机 DRAM

当显存不足时,将部分 KV Cache 移动到 CPU 主机内存中.

需要考虑:
- 哪些 KV 可以被逐出;
- 什么时候逐出;
- 每次搬运多大数据块;
- KV 如何在 DRAM 中定位;
- 需要时如何回读到 GPU;
- GPU 是否必须等待回读完成.

这一步的目标通常是:

> 用主机内存扩大有效 KV 容量,同时观察 PCIe 搬运代价.

### 第三层: 加入 SSD

进一步把更冷的数据放到SSD:

``` plaintext
GPU 显存 → CPU DRAM → SSD
SSD → CPU DRAM → GPU 显存
```

需要处理:
- SSD 上的数据布局;
- KV 分块;
- 块地址和元数据;
- 写回;
- 按需读取;
- O_DIRECT 或 SPDK;
- 预取;
- 双缓冲;
- 异步 I/O.

这一阶段才是最主要的系统研究内容.

### 第四层: 让搬运和计算重叠

最朴素的实现是:

``` plaintext
先从 SSD 读取 KV
读取完成
再开始 GPU 计算
```

但是!这样GPU会频繁等待I/O

更好的方式是:

``` plaintext
GPU 正在计算第 i 个块
        同时
CPU/SSD 提前读取第 i+1 个块
```

这叫:
- 预取:提前读取之后可能用到的数据;
- 流水线:让读取,传输和计算并行进行;
- 双缓冲:一个缓冲区供 GPU 使用,另一个缓冲区同时接收下一批数据;
- 异步搬运:提交数据传输后,不立即阻塞等待.

理想的时间关系是:

``` plaintext
计算第 1 块 ─────────────
读取第 2 块 ───────
计算第 2 块       ─────────────
读取第 3 块             ───────
```

## 8. `vLLM`和`Mooncake`分别是什么?

### `vLLM`

**vLLM是一个LLM推理服务框架**

它负责很多事情:
- 调用模型(加载LLM);
- 接收请求;
- 调度请求;
- 调度 batch;
- 执行 prefill 和 decode;
- 管理 KV Cache;
- 管理 GPU 显存;
- 提高吞吐和并发能力;
- 生成回答.

如果没有vLLM,需要另外实现很多底层功能:
- 模型加载;
- tokenizer;
- Transformer forward;
- batch 调度;
- CUDA 执行;
- token 生成;
- KV Cache 分配;
- 服务接口.

vLLM负责的链路:

``` plaintext
接收请求
    ↓
安排多个请求如何一起运行
    ↓
调用 Transformer 模型
    ↓
管理 GPU 显存和 KV Cache
    ↓
生成 token
    ↓
返回结果
```

更多关于 PagedAttention、调度器与前缀缓存的细节见 [认识 vLLM](./03-认识vLLM.md)。

### `Mooncake`

**Mooncake是一个围绕KV Cache组织的系统架构和实现**

它关注:
- KV Cache 的共享;
- KV Cache 的存储;
- KV Cache 的传输;
- 不同节点之间的协作;
- 存储资源的利用;
- Prefill 和 Decode 的分离;
- 把 KV 当作一种可以调度的**系统资源**.

于是可能存在这样的场景:

``` plaintext
服务器 A：负责处理输入和 Prefill
服务器 B：负责 Decode

服务器 A 之前处理过类似前缀
服务器 B 收到新的请求
        ↓
服务器 B 查询共享缓存
        ↓
找到可复用的 KV
        ↓
传输到服务器 B 的 GPU
```

实际项目中不一定需要从零实现MoonCake,更现实的路线通常是:

``` plaintext
先使用 vLLM 跑通推理
        ↓
理解它的 KV 管理接口
        ↓
接入或参考 LMCache / Mooncake
        ↓
实现自己的简化分层缓存原型
```

更多关于 Transfer Engine、Mooncake Store 与协同架构的细节见 [认识 Mooncake](./04-认识Mooncake.md)。

## 9. 最后串联起整个项目的主线任务

大概长这样:

``` plaintext
理论
  ↓
单机 vLLM Baseline
  ↓
GPU ↔ DRAM
  ↓
GPU ↔ DRAM ↔ SSD
  ↓
预取与异步优化
  ↓
单机完整评测
  ↓
再做 Mooncake 多机扩展
```
